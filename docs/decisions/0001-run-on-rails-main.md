# 0001. Run on Rails Main

- **Status:** Accepted
- **Date:** 2026-10-17
- **Revisit:** 2026-12-17, or sooner if a trigger below fires

## Context

codegym is a practice gym for programmers, with a coach that makes you do the thinking. It is also a vehicle for getting better at Rails by building something large and real.
 
When this was decided, Rails main was `8.2.0.alpha` (requires Ruby >= 3.3.5). The current stable line was 8.1 (8.1.4 released 2026-09-24). No 8.2 or 9.0 beta had been announced.
 
"Cutting edge" here means Rails itself, not a pile of new gems. The aim is to meet framework changes while they are still being made, to read them as diffs, and to feed problems back upstream where that is useful.

## Decision
 
Track `rails/rails` `main` from the first commit.
 
- `Gemfile` points at `github: "rails/rails", branch: "main"`.
- `Gemfile.lock` is committed, so the app is always pinned to an exact SHA. We move that SHA on purpose and never as a side effect of `bundle update`.
- The baseline SHA is recorded in the bump log below before any feature work starts.

## Rules
 
1. **Bump weekly, as its own commit.** Update Rails only, run `bin/ci`, fix what broke, and commit with the old and new SHA in the message. Use `bin/bump-rails`.
2. **Read before bumping.** Skim the latest *This Week in Rails* and the diff between the two SHAs. Write down anything that changed how we would write code.
3. **Keep the basics boring.** The library, exercise pages, and attempt log are plain Rails. Main-only features are reserved for the parts of the app where we are exploring anyway: the coach, background jobs, and telemetry.
4. **Every framework change that bites goes in the bump log.** Date, SHA range, what broke, and what we learned.
5. **Prefer upstream over workarounds.** If the cause is Rails, reduce it to a minimal reproduction and file an issue (or a PR) before adding a local patch. Any patch we do keep gets a comment with a link and a removal condition.

## Consequences
 
**Good**

- We see changes while they are small and still discussable.
- Weekly bumps keep each upgrade tiny. There is never a big-bang upgrade later.
- Real material for the skill we are trying to build: reading framework diffs and reasoning about them.

**Bad**
- Some gems will lag or break against main. Time lost to that is part of the cost.
- Main can regress. A bad week can stall product work.
- Documentation may trail behavior. The source and the edge guides are the reference.

## Escape hatch
 
Move to the stable 8.1 line (`gem "rails", "~> 8.1"`) if any of these happen:
 
- The app has been unable to run `bin/ci` green for more than 7 days because of the framework.
- A needed gem has no workable path on main and the fix is not close.
- Product work has stalled for two consecutive weeks on framework issues.
Switching is a Gemfile change plus `bin/rails app:update`. Record the switch as a new decision that supersedes this one. Do not edit this file after the fact.
